# 青芽 · Android 习惯打卡市场调研与产品决策

调研日期：2026-11-06（Asia/Shanghai）。调研类型：一手公开资料桌面研究。本文是设计依据，不是已实现功能清单；实际交付范围见 README。

## 1. 结论与证据边界

建议做一款中文、离线优先、无需注册的个人习惯工具：打开即看见今天要做的事，完成动作立即获得轻微触感和树木成长反馈，历史积累在一次中断后仍然保留。核心价值是“更容易回来继续”，不是把用户变成一个永远不能断签的数字。

调查覆盖 9 款产品：纯习惯管理、任务一体化、游戏成长、自我照顾、专注计时、纪念日。来源为开发者官网、官方帮助中心、官方源码和开发者提交的应用商店介绍。未实际安装全部竞品，未做用户访谈、付费体验或帧率实测；因此“交互启示”均为设计推论，不把宣传文案当作可用性实验结论。商店下载量、评分和价格有地区与时间差异，本报告不以其作为排名依据，也不编造当前价格。

特别注意同名产品：本文 Loop 指 `org.isoron.uhabits`，不是搜索中出现的同名 iPhone 产品；小日常 Android 指广州小日常科技有限公司、包名 `com.dandelion.routine`。Streaks 仅作为 Apple 平台交互参考；Days Matter 是相邻品类，不是完整习惯追踪器。跨平台版本能力不互相推定。

## 3. 从观察到设计决策

### 明确的市场共性

- **完成入口要近。** Loop 的通知/组件、HabitNow 的组件、小日常的快捷打卡、Finch 的首页目标都把记录放在日常触达处。首版首页直接呈现当天习惯，完成无需进入详情。
- **计划有节奏。** 多款产品支持非每日频率，因此统计分母应是“应完成的计划日”，不能机械地把休息日算失败。
- **统计是反馈，不是数据堆。** 今天进度、最近一周和月历足以形成第一层回顾；年度图、复杂筛选可后置。
- **成长提供记忆点。** Forest 的森林和 Finch 的伙伴让累计投入可视化。树木成长与当前项目名称匹配，且可用原创矢量绘制保持包体轻。
- **离线不等于永不丢失。** Loop 的导出和 Finch 的备份说明用户需要数据迁移能力。离线产品必须清楚说明卸载和换机风险，并提供可验证的导入/导出。

上述为跨来源综合判断，不是统计意义上的市场需求验证。首批用户测试应验证完成速度、重复使用动机、提醒容忍度和断签后的回归率。

### 推荐定位

调研阶段候选名为“树生”，最终确定为“青芽 Qingya”。主文案：“让每一次坚持，慢慢长成一棵树。” 服务对象为希望坚持阅读、喝水、运动、学习等个人目标、又不希望使用社交排行榜的人。

首轮体验：选一个模板或自定义 → 确认名称/目标/重复日 → 首页完成第一次 → 看见真实累计成长。提供模板但不伪造历史，不预置“已完成”数据充当用户成绩。

## 4. MVP 与后续边界

| 优先级 | 能力 | 可验证的完成标准 |
| --- | --- | --- |
| P0 | 习惯创建、编辑、归档/删除 | 名称验证；修改不误清历史；破坏性操作可确认；重启后保留 |
| P0 | 当日打卡与撤销 | 点击后立即反馈；快速重复点不会重复奖励；撤销同步更新统计 |
| P0 | 频率与目标 | 至少支持按星期重复；若有数量目标，部分完成不应误计为完成 |
| P0 | 真实历史与统计 | 日历可查看记录；区分未来、休息日、未完成、完成；历史补记语义明确 |
| P0 | 本地保存与备份 | 首次无网可用；导出再导入得到等价状态；坏文件不会破坏当前数据 |
| P0 | 发布更新 | 使用长期签名发布 APK；应用可发现更高版本并走可恢复的下载/安装流程 |
| P1 | 提醒 | 在用户启用时申请通知权限；拒绝后仍可打卡；调整计划后取消旧提醒 |
| P1 | 动效与无障碍 | 原创成长视觉；支持减少动态/系统动画关闭；文字放大和触屏操作可用 |
| P2 | 桌面组件、专注计时、更多成长主题 | 核心可靠性之后再扩展 |
| 暂缓 | 社交、排行榜、账号、云同步、AI 教练、订阅 | 避免首版同时承担服务端、内容与商业化复杂度 |

数据规则建议：每个习惯有稳定 ID；记录以用户本地日历日期绑定；计算统计时只纳入已开始且计划执行的日期；历史目标或频率变更需要保留当时语义，或明确只对未来生效。归档与删除分开；成长是可由真实记录重算的结果，而不是独立累加且难以撤销的随机积分。

## 5. 视觉与动效方案（本项目设计建议）

### 视觉

使用温暖纸白背景、深森林绿文字、苔藓绿主色、少量杏黄色点缀。首页优先级：日期与问候 → 原创树木成长卡 → 今日列表 → 底部导航。主体内容比装饰更醒目，植物图形避开文字区；列表使用一致的圆角和轻边界，不依赖大面积阴影。

底部导航建议“今天 / 成长 / 我的”；新建入口稳定可见。空状态给出一个可行动建议；完成全部时显示庆祝与回顾入口，不用全屏弹窗阻断用户。统计页面先呈现一句可理解的结果，再展现周分布和月历。

### 动效契约

这些数值是初始实现目标，需设备验证，而非竞品实测结论。

| 触发 | 反馈 | 初始时长 | 性能/可访问性约束 |
| --- | --- | --- | --- |
| 按下打卡 | 按钮轻缩与可选触感 | 80–120ms | 保持点击命中区，不延迟实际保存 |
| 完成 | 勾号/填色过渡、进度变化 | 180–280ms | 动画中不阻止继续操作，完成与未完成不能只靠颜色区别 |
| 植物成长 | 叶片轻弹、有限粒子 | 450–650ms | 只在进度真实变化时播放，离屏停止，不循环消耗电量 |
| 切换页面 | 短距离位移和淡入 | 180–240ms | 保持返回导航可预测，避免大幅晃动 |
| 减少动态 | 即时状态或简单淡入 | 0–100ms | 仍有文字和图标反馈 |

树木成长依据累计完成事件，漏做不枯萎。今日完成率可以重置，累计树木不随午夜退化。连续天数可展示，但主奖励采用累计里程碑；休息日不破坏合理的计划连续性。所有庆祝文案避免羞耻与道德评判，例如“今天也长大了一点”“休息之后，随时再开始”。

## 6. Android 分发与自动更新

### 本项目 GitHub APK 渠道建议

1. 固定包名、长期保存正式签名密钥，未来发布递增 `versionCode`。Android 要求 APK 安装和更新必须签名，密钥管理属于持续发布基础。[Android 应用签名](https://developer.android.com/studio/publish/app-signing)
2. 发布流程生成正式 APK、SHA-256、版本号和更新说明，再上传 GitHub Release。应用从固定可信来源检查较新版本，优先使用版本清单，不把未经验证的远程任意 URL 直接送给安装器。
3. 自动检查可以发生在前台启动及低频后台任务；检测成功显示可忽略提示。用户确认后下载，校验文件散列和包身份，再交给系统安装器。断网、限流、下载失败或没有新版本不能影响打卡。
4. Android 8+ 为每个安装来源设置用户信任。直接请求安装前检查 `canRequestPackageInstalls()`，必要时引导到该应用的“允许安装未知应用”设置，返回后继续流程。[PackageManager 官方 API](https://developer.android.com/reference/android/content/pm/PackageManager.html#canRequestPackageInstalls())
5. 对用户准确表述为“自动检查新版本，确认后下载并安装”。Android 12+ 提供特定条件下免用户动作的更新机制，但需要目标 API、安装者/更新拥有者或自更新身份及相应权限，且官方仍要求处理 `STATUS_PENDING_USER_ACTION`；不可承诺所有设备完全静默安装。[PackageInstaller.SessionParams](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int))
6. WorkManager 周期任务受省电和 Doze 影响，不保证整点执行；官方最小周期为 15 分钟。检查更新建议每天一次或前台间隔节流，不做分钟级轮询。[PeriodicWorkRequest](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest.html)

上面第 2、3 点的校验顺序和交互是本项目工程建议。SHA-256 防止传输损坏，不应被描述为独立于发布源的可信证明；最终还依赖 Android 签名检查及安全的密钥和仓库权限。

### 将来 Google Play 渠道

Google Play 提供 Flexible 和 Immediate 两种 In-App Updates：前者允许使用期间下载，后者要求先完成更新再继续。习惯工具通常适合前者。[Play In-App Updates](https://developer.android.com/guide/playcore/in-app-updates)

Play 对 `REQUEST_INSTALL_PACKAGES` 有严格的核心用途限制。因此未来应区分 GitHub 与 Play 构建渠道，Play 版使用 Play 更新流程，不直接照搬自下载 APK 的权限清单。[Play 权限政策](https://support.google.com/googleplay/android-developer/answer/12085295?hl=en)

## 7. 首发验证清单

- 核心行为：新建、打卡、撤销、编辑、归档/删除、跨日、非计划日、重启恢复。
- 数据：时区/日期切换、备份往返、坏备份、升级保留记录、相同日重复操作的幂等性。
- 展示：小屏、大字体、长中文名称、深浅主题（若提供）、空状态、全完成状态。
- 性能：真实 Android 设备或模拟器滚动和动效检查，记录可观察结果；不能仅凭构建成功宣称 60fps。
- 更新：无网络、无新版、有新版、下载失败、散列不符、安装权限拒绝、用户取消、同签名覆盖升级。
- 发布：Release 资产可匿名下载、校验和对应、版本与包名正确、签名密钥不入库、构建说明可复现。

## 8. 后续用户验证

建议首轮邀请 5–8 名中文 Android 用户完成“建立一个习惯 → 打卡 → 撤销 → 回顾 → 导出”任务，记录完成时间和卡点；随后观察两周。重点询问“漏做一天后是否愿意回来”，而非只问界面好不好看。没有用户数据前，不声称提高了坚持率或改善心理健康。
